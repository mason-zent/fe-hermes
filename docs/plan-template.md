# 작업계획서 템플릿

파일명: `plans/작업유형/YYYYMMDD-제목.md` (+ 같은 이름의 `.html`)

## ⚠️ md + html 동시 생성 (필수)

- HTML은 `docs/plan-template.html`을 복사해 **두 블록만** 채운다 (스타일/스크립트는 그대로).
  - **[A] `<script id="plan-data">`의 `PLAN`**: title/type/scope/mdFile/summary + `decisions[]` (`.md`의 "사용자 결정 사항"과 1:1)
  - **[B] `<script id="plan-md">`**: `.md` 본문을 그대로 붙여넣기
- 승인 전 → `decisions[]`에 `options`만. 확정 후 → 각 결정에 `decided` 채움
- `.md` ↔ `.html`은 **같은 턴에 함께 갱신**

---

## 템플릿

```markdown
# [제목]

## 1. 개요
- 작업 유형: feature / bugfix / refactor
- 요청 사항: (사용자 요청 요약)
- 대상 서비스(에이전트): refund-fe / hub-fe / care-fe / op-fe / bznav-{refund,care,brand,sena,plus}-fe / bznav-packages-fe / packages-fe (복수 가능)
- 사용자 결정 사항: (선택지가 갈리는 항목 — 이 목록이 `.html`의 `decisions[]`가 된다)
  - 결정 항목 1: **선택값** (옵션 후보 나열)

## 2. 현재 상태 분석
- 서비스별 관련 기존 코드 (파일 경로, 주요 로직)
- 재사용 가능한 컴포넌트/훅/유틸
- 기존 API (Orval 생성물 / GraphQL 스키마 / gateway) 중 사용할 것

## 3. API 의존성
- 기존 엔드포인트 사용: `METHOD /path` — 응답 타입 (생성물 이름)
- 신규/변경 필요 (외부 의존, 백엔드 팀 요청 사항):
  | 엔드포인트 | 요청 | 응답 | 상태 |
  |---|---|---|---|
  | ... | ... | ... | 요청 필요 / 진행 중 / 완료 |
- 백엔드가 준비되지 않았을 때의 처리 방식 (임시 훅 / mock / 대기)

## 4. 화면 설계 (서비스별)
### refund-fe (예)
- 라우트: /path, 권한: PAGE_XXX (가드 위치)
- 컴포넌트 구조 (간략), 상태 관리 방식, 데이터 페칭
- 네비게이션/메뉴 위치

## 5. 공통 스펙 (복수 서비스일 때)
- 서비스 간 동일해야 하는 문구·동작·env 키 이름
- 공유 패키지 변경 필요 여부 (있으면 "외부 의존"으로 표기)

## 6. 작업 배분

| 담당 | 작업 내용 | 의존성 |
|------|----------|--------|
| refund-fe | ... | 없음 |
| hub-fe | ... | 없음 |
| reviewer | 계획서 대비 검증 + 교차 정합성 | FE 완료 후 |

## 7. 병렬 작업 근거 / 검증 방법
- 서비스별 작업이 독립적인 이유
- 각 서비스 검증 명령 (lint / typecheck / test)
```

## 작성 원칙
1. **라우팅이 먼저**: 어느 서비스 작업인지, 왜 그 서비스인지 명시
2. **재사용 우선**: 기존 컴포넌트·훅·생성물을 먼저 찾고 새로 만들 것을 최소화
3. **외부 의존 분리**: 백엔드·공유 패키지 변경은 "외부 의존"으로 따로 적어 사용자가 판단하게 한다
4. **간결하게**: spec과 배분에 집중
5. **결정은 HTML로**: 사용자가 골라야 하는 항목은 결정 콘솔에 담아 클릭→복사로 확정받는다
