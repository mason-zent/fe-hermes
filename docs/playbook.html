슬래시 커맨드는 헤르메스 세션에서만 씁니다. FE 에이전트 pane 에는 슬래시 커맨드가 아예 노출되지 않습니다(도구는 Read·Edit·Write·Bash 뿐). 라우팅·계획서·디스패치는 팀리드의 일이지 담당 엔지니어의 일이 아니기 때문입니다.

에이전트 pane 에서는 평문으로 그냥 지시하면 됩니다. 그 pane 은 담당 레포가 이미 고정되어 있으므로(하단 상태바에 표시됩니다) refund 같은 레포 접두사도 붙일 필요가 없습니다.

사용자 승인

사용자
  • 정식: 헤르메스가 md 와 같은 이름의 html 결정 콘솔을 만들어 현황판 주소로 열어 줍니다(대화에는 경로와 결정마다 제목·추천 한 줄). 콘솔에서 고르고 [이대로 진행]을 누르면 결정이 그 계획서를 만든 헤르메스 pane 에 바로 들어갑니다 → md·html 에 확정값을 적고 "✅ 확정". 대화로 "추천대로", "D2 는 B" 라고 답해도 됩니다. 경량에는 결정 콘솔이 없습니다.

  • 커밋은 사용자가 "커밋해줘"라고 할 때만 scripts/commit.sh로 합니다 — 지정 파일만·엄격 검증·계획서 ## Commits 기록. 메인 체크아웃·보호 브랜치·검증 실패면 거부합니다.
  • 레포 하나짜리 작업은 여기서 PR 까지 — 코드를 바꾼 요청을 보고하면 에이전트가 묻지 않고 바로 옆에 reviewer pane 을 띄웁니다(자동 리뷰). 결론이 나오면 보여 주고, 수정 필요면 무엇을 고칠지 묻습니다. "리뷰해줘"로 다시 받을 수도 있고, "PR 올려줘"면 scripts/ship.sh 가 base 후보·올라갈 커밋·검증·리뷰 기록·제목 제안·본문 초안을 보여 준 뒤 확인받아 draft PR 을 엽니다. 커밋 안 된 변경, commit.sh 를 안 거친 커밋, 여러 레포 작업, 형식에 안 맞는 제목은 거부합니다.

검증 · 보고 · push/PR

reviewer · 헤르메스
  • 여러 레포 작업이나 헤르메스가 맡은 작업은 헤르메스에게 "리뷰해줘" — reviewer 가 계획서와 워크트리를 받아 diff를 읽고 검증 스크립트를 다시 돌려 에이전트 보고와 비교합니다. 수정 필요 항목은 사용자 확인 뒤 그 FE pane 에서 이어서 지시합니다.
  • 서비스별 변경 파일·주요 변경·검증 결과·## Commits·남은 위험을 요약합니다. 검증 실패는 숨기지 않습니다.
  • 여러 레포에 걸친 작업의 push·PR 은 헤르메스가 순서(공유 패키지 먼저)·공개 범위를 확인하고 사용자에게 물은 뒤 레포마다 ship.sh --repo-agent 로 올립니다. 레포 하나짜리는 에이전트 pane 에서 올립니다(4단계).

정리

헤르메스
  • 끝난 카드는 현황판 완료 칸의 [아카이브] — 이슈와 계획서를 archive/<이름>/ 한 폴더로 묶어 보관하고 git 에 커밋합니다. 이슈 워크트리도 정리합니다(미커밋·push 안 된 커밋이 있으면 남김). 지나간 일은 현황판 [히스토리] 탭에서 검색합니다.
  • 이슈는 완료 기준이 채워지면 완료 가능 배지가 붙고 헤르메스가 완료로 옮깁니다. 안전망: scripts/archive-plans.sh(30일 이상 + 최근 git log 미언급).

규칙

규칙은 세 층입니다. 팀 공통(docs/knowledge/common/: 코드·Git·보고) → 레포 규칙(docs/knowledge/<레포>/rules.md: 공통과 다른 점) → 레포 원문(.ai/basic-rule.md, 레포 CLAUDE.md 등). 충돌하면 뒤가 우선합니다. 아래 .claude/rules/는 헤르메스 자신의 운영 규칙 요약입니다.

git-workflow

  • FE 에이전트는 사용자가 pane 에서 "커밋해줘" 라고 할 때만 scripts/commit.sh 로 로컬 커밋(지정 파일만·엄격 검증·계획서 기록). push·PR 은 "PR 올려줘" 일 때 scripts/ship.sh 로(레포 하나짜리, draft)
  • PR 제목 type(범위): 티켓 요약 · 본문 공통 템플릿 (git.md "PR 제목·본문")
  • 시작 전 git status로 기존 변경 확인, 무관한 파일은 건드리지 않음
  • 커밋 메시지는 한국어, 티켓 있으면 feat: REF-1234 설명

coding-standards

  • 기존 패턴 분석 후 그 패턴을 따름
  • 범위 밖 정리·의존성 업그레이드·파일 이동·전역 포맷팅 금지
  • 1글자 변수명, 3항 중첩, 새 코드의 any 금지
  • 요청 안 한 범용화·옵션·prop 금지. 필요한 분리와 상태·오류·보안 처리는 유지
  • 이번 변경으로 생긴 미사용 코드만 정리, 기존 것은 보고·이슈 등록
  • 같은 오류 3회 반복 시 접근 재검토 후 보고

dispatch-protocol

  • 계획서(정식은 승인 후 · 경량은 지시가 곧 승인)가 있어야 디스패치 — delegate.sh --plan 필수
  • 독립 작업은 한 응답에서 동시 호출
  • 결과 보고에서 변경 파일·검증 결과·남은 위험 확인

language

  • 한국어로 소통, 주석도 한국어
  • 영어는 코드·파일명·기술 용어만
  • 불확실하면 "추측입니다"라고 명시

확장하기

스킬(슬래시 커맨드)과 에이전트는 파일 하나로 추가됩니다. 추가한 뒤에는 문서 몇 곳을 같이 손봐야 합니다. 같은 내용이 docs/extending.md에 있고, 터미널에서 /guide로 바로 볼 수 있습니다.

스킬 추가

  • .claude/skills/<이름>/SKILL.md 하나 만들면 /<이름>으로 바로 뜹니다
  • frontmatter에 name, description, 필요하면 argument-hint를 둡니다
  • 본문에서 $ARGUMENTS로 인자를 받습니다
  • 기존 call/SKILL.md를 복사해서 고치는 게 가장 빠릅니다

에이전트 추가

  • .claude/agents/<이름>.md 하나 만들면 됩니다
  • frontmatter의 description은 헤르메스가 라우팅할 때 읽는 문장입니다. "어떤 요청이면 이 에이전트"를 구체적으로 적어주세요
  • description 안에 콜론+공백(: )이 들어가면 YAML이 깨집니다

자주 묻는 질문

슬래시 커맨드를 꼭 써야 하나요?
아니요. "refund 파트너 목록에 검색 추가해줘"처럼 말하면 CLAUDE.md 규칙에 따라 헤르메스가 같은 흐름으로 움직입니다. 커맨드는 흐름을 확실히 타게 하는 단축키입니다.
에이전트를 직접 지정할 수 있나요?
가능합니다. "hub-fe로 메시지 큐 화면에 컬럼 하나 추가해줘"라고 하면 헤르메스가 hub-fe에 넘깁니다. 단, 계획서를 건너뛸지는 헤르메스가 작업 크기를 보고 판단하며, 규모가 있으면 계획서를 먼저 씁니다.
급한 수정은 어떻게 하나요?
"바로 고쳐"라고 명시하면 결정 콘솔 단계를 건너뛰고 경량 계획서(plans/task/…, 사용자 지시가 곧 승인)로 바로 디스패치합니다. 계획서 없이 디스패치하는 예외는 없습니다. reviewer 검증은 그대로 진행합니다.
백엔드 API가 아직 없는데 화면부터 만들 수 있나요?
계획서의 "API 의존성" 항목에 필요한 엔드포인트와 응답 타입을 적고, 백엔드가 준비될 때까지의 처리 방식(임시 훅 / mock / 대기)을 결정합니다. refund-fe와 hub-fe는 Orval 생성물이 없을 때 lib/swr 패턴으로 임시 훅을 만들고 보고에 명시하도록 되어 있습니다.
공유 패키지(brics-fe-ui 등)를 고쳐야 하면요?
FE 에이전트는 직접 고치지 않고 헤르메스에 보고합니다. 헤르메스는 이를 "외부 의존"으로 사용자에게 알리고, zent-packages 작업은 별도로 진행합니다.
레포가 바뀌면 에이전트 문서는 누가 고치나요?
/sync를 치면 헤르메스가 담당 레포의 운영 기준 브랜치(콘솔·모바일 앱은 prd, bznav는 앱별 prd-<앱>·packages는 dev, zent-packages는 main — 표는 /sync 카드)를 읽어 바뀐 사실(버전·명령·포트·구조·포맷·규칙 문서)만 골라 문서를 고칩니다. 자동으로 상시 감시하지는 않으니, 세션을 시작할 때 문서가 오래된 것 같으면 한 번 돌려주세요. 판단이 들어간 문장은 자동으로 바꾸지 않고 "확인 필요"로 알려줍니다.
reviewer는 왜 따로 있나요?
작업한 에이전트가 자기 코드를 검증하면 놓치는 부분이 있습니다. reviewer는 읽기 전용으로 계획서 대비 누락·초과, 레포 규칙 준수, 여러 서비스에 같은 기능을 넣었을 때의 문구·동작·env 키 일관성을 봅니다. 필요 없으면 .claude/agents/reviewer.md 하나만 지우면 됩니다.
