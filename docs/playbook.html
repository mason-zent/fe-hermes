작업 흐름

헤르메스는 어떤 요청이든 아래 순서로 움직입니다. 핵심은 2단계입니다. 승인 전에는 어떤 에이전트도 파일을 건드리지 않습니다.

분석 · 계획서 작성

헤르메스
  • 대상 서비스를 정하고, 해당 레포에서 관련 기존 코드와 재사용 가능한 컴포넌트·훅·API 생성물을 찾습니다.
  • plans/유형/YYYYMMDD-제목.md와 같은 이름의 .html을 한 쌍으로 만듭니다. md는 상세 스펙, html은 결정 콘솔 겸 읽기 뷰입니다.
  • 백엔드나 공유 패키지 변경이 필요하면 "외부 의존"으로 따로 적습니다.

사용자 승인

사용자
  • HTML을 열어 갈리는 선택지를 고르고 [프롬프트로 복사]를 눌러 채팅에 붙여넣습니다.
  • 헤르메스가 결정대로 md를 확정하고 html에 decided를 채우면 "확정 완료" 뷰로 바뀝니다.

병렬 디스패치

헤르메스 → FE 에이전트
  • 독립적인 서비스 작업은 한 응답에서 동시에 호출합니다.
  • 프롬프트에는 계획서 경로, 자기 담당 범위, 관련 파일, API 스펙, 다른 서비스와의 연관성, "커밋 금지·레포 밖 수정 금지" 리마인드가 들어갑니다.
  • 여러 서비스에 같은 기능을 넣을 때는 계획서의 공통 스펙(문구·동작·env 키)을 모두가 같이 봅니다.

검증

reviewer
  • 계획서 경로와 대상 레포를 받아 diff를 읽고, 각 레포의 lint·typecheck·test를 실행합니다.
  • 수정 필요 항목은 해당 FE 에이전트에 재디스패치합니다. 검증 실패는 숨기지 않고 그대로 전달합니다.

보고

헤르메스
  • 서비스별 변경 파일, 주요 변경, 검증 결과, 남은 위험을 요약합니다.
  • 이 시점까지 커밋은 되어 있지 않습니다. 커밋과 PR은 사용자가 결정합니다.

정리

헤르메스
  • 작업 종료가 확인되면 계획서를 plans/archive/유형/으로 옮깁니다. 후속 작업이 남았으면 그대로 둡니다.
  • scripts/archive-plans.sh가 30일 이상 지났고 최근 git log에 언급되지 않은 계획서를 일괄 정리합니다.

규칙

.claude/rules/에 있는 공통 규칙입니다. 레포별 포맷·스택 규칙은 각 에이전트 파일이 우선합니다.

git-workflow

  • FE 에이전트는 커밋하지 않음. 커밋 여부는 사용자에게 확인
  • 시작 전 git status로 기존 변경 확인, 무관한 파일은 건드리지 않음
  • 커밋 메시지는 한국어, 티켓 있으면 feat: REF-1234 설명

coding-standards

  • 기존 패턴 분석 후 그 패턴을 따름
  • 범위 밖 정리·의존성 업그레이드·파일 이동·전역 포맷팅 금지
  • 1글자 변수명, 3항 중첩, 새 코드의 any 금지
  • 같은 오류 3회 반복 시 접근 재검토 후 보고

dispatch-protocol

  • 승인된 계획서가 있어야 디스패치
  • 독립 작업은 한 응답에서 동시 호출
  • 결과 보고에서 변경 파일·검증 결과·남은 위험 확인

language

  • 한국어로 소통, 주석도 한국어
  • 영어는 코드·파일명·기술 용어만
  • 불확실하면 "추측입니다"라고 명시

확장하기

스킬(슬래시 커맨드)과 에이전트는 파일 하나로 추가됩니다. 추가한 뒤에는 문서 몇 곳을 같이 손봐야 합니다. 같은 내용이 docs/extending.md에 있고, 터미널에서 /guide로 바로 볼 수 있습니다.

스킬 추가

  • .claude/skills/<이름>/SKILL.md 하나 만들면 /<이름>으로 바로 뜹니다
  • frontmatter에 name, description, 필요하면 argument-hint를 둡니다
  • 본문에서 $ARGUMENTS로 인자를 받습니다
  • 기존 feature/SKILL.md를 복사해서 고치는 게 가장 빠릅니다

에이전트 추가

  • .claude/agents/<이름>.md 하나 만들면 됩니다
  • frontmatter의 description은 헤르메스가 라우팅할 때 읽는 문장입니다. "어떤 요청이면 이 에이전트"를 구체적으로 적어주세요
  • description 안에 콜론+공백(: )이 들어가면 YAML이 깨집니다

같이 갱신할 곳

  • CLAUDE.md의 팀 표·Skills 표
  • README.md
  • docs/playbook.html (이 문서)
/sync는 레포 쪽 변화만 반영하고 hermes 자체 구조 변화는 잡지 않습니다. 스킬이나 에이전트를 추가했으면 헤르메스에게 "방금 추가한 스킬 문서에도 반영해줘"라고 하면 위 세 곳을 갱신합니다.

자주 묻는 질문

슬래시 커맨드를 꼭 써야 하나요?
아니요. "refund 파트너 목록에 검색 추가해줘"처럼 말하면 CLAUDE.md 규칙에 따라 헤르메스가 같은 흐름으로 움직입니다. 커맨드는 흐름을 확실히 타게 하는 단축키입니다.
에이전트를 직접 지정할 수 있나요?
가능합니다. "hub-fe로 메시지 큐 화면에 컬럼 하나 추가해줘"라고 하면 헤르메스가 hub-fe에 넘깁니다. 단, 계획서를 건너뛸지는 헤르메스가 작업 크기를 보고 판단하며, 규모가 있으면 계획서를 먼저 씁니다.
급한 수정은 어떻게 하나요?
"계획서 없이 바로 고쳐"라고 명시하면 계획서 단계를 건너뜁니다. 헤르메스는 보고에 그 사실을 남기고, reviewer 검증은 그대로 진행합니다.
백엔드 API가 아직 없는데 화면부터 만들 수 있나요?
계획서의 "API 의존성" 항목에 필요한 엔드포인트와 응답 타입을 적고, 백엔드가 준비될 때까지의 처리 방식(임시 훅 / mock / 대기)을 결정합니다. refund-fe와 hub-fe는 Orval 생성물이 없을 때 lib/swr 패턴으로 임시 훅을 만들고 보고에 명시하도록 되어 있습니다.
공유 패키지(brics-fe-ui 등)를 고쳐야 하면요?
FE 에이전트는 직접 고치지 않고 헤르메스에 보고합니다. 헤르메스는 이를 "외부 의존"으로 사용자에게 알리고, zent-packages 작업은 별도로 진행합니다.
레포가 바뀌면 에이전트 문서는 누가 고치나요?
/sync를 치면 헤르메스가 담당 레포의 origin/dev(zent-packages는 main)를 읽어 바뀐 사실(버전·명령·포트·구조·포맷·규칙 문서)만 골라 문서를 고칩니다. 자동으로 상시 감시하지는 않으니, 세션을 시작할 때 문서가 오래된 것 같으면 한 번 돌려주세요. 판단이 들어간 문장은 자동으로 바꾸지 않고 "확인 필요"로 알려줍니다.
reviewer는 왜 따로 있나요?
작업한 에이전트가 자기 코드를 검증하면 놓치는 부분이 있습니다. reviewer는 읽기 전용으로 계획서 대비 누락·초과, 레포 규칙 준수, 여러 서비스에 같은 기능을 넣었을 때의 문구·동작·env 키 일관성을 봅니다. 필요 없으면 .claude/agents/reviewer.md 하나만 지우면 됩니다.
